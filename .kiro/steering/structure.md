# Repo Structure & Boundaries

```
real-state/                  ← REPO ROOT = the Kiro workspace root (open THIS in Kiro)
├── .kiro/                   ← IDE config (steering, hooks, settings/mcp.json) — loaded from root
├── README.md
├── docs/
│   ├── kiro-prompts/        ← build plan for the FastAPI service (one prompt per file, 01→17)
│   ├── wix-site/            ← independent Velo project (/backend /pages /public) — paste into Wix
│   ├── wix-integration/     ← Wix design + setup DOCS (architecture, SETUP.md)
│   └── IDE_CONFIG.md        ← how the .kiro config fits together
└── realestate-media-api/    ← (generated by docs/kiro-prompts/01-scaffold.md)
```

> **Workspace root is the repo root**, because `.kiro/` lives there. Open the repo root in Kiro,
> NOT `docs/` — opening `docs/` would leave `.kiro/` outside the workspace and silently disable all
> steering + hooks. Every path below is relative to the repo root.

When the FastAPI service is generated, it lives in its own folder (`realestate-media-api/`) at the
repo root, with the layout defined in `docs/kiro-prompts/01-scaffold.md`:
`app/{config,deps,pricing}.py`, `app/{schemas,obs,providers,pipeline,wallet,jobs,routers}/`.

## Hard boundaries (do not cross)
- **`docs/wix-site/` never imports the Python service** and vice-versa. They communicate only over
  HTTPS with HMAC-signed requests.
- **Balance/money logic lives only in Wix** (`docs/wix-site/backend/lib/wallet.js`). The FastAPI side
  keeps an audit ledger, never an authoritative balance.
- **Secrets never live in code or git** — Wix Secrets Manager and FastAPI `.env` (gitignored).
- Keep the Velo `/backend /pages /public` layout intact; backend `lib/*` are internal modules,
  `*.web.js` are the only frontend-callable surface, `http-functions.js` is the only inbound HTTP.

## Naming
- Python: snake_case modules, typed everything. FastAPI routers grouped by resource.
- Velo: web methods are verbs (`getQuote`, `submitMediaKit`); internal libs are nouns.
